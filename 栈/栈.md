## 阶段一：数据结构层面的 Stack（伪装在堆上的屏障）

### 1. 核心认知：Stack 的物理虚无主义
在物理内存中，**不存在“栈”这种硬件结构**（指数据结构层面）。
`std::stack` 本质上只是一个**读写屏障（Access Barrier）**。它剥夺了你随机访问（Random Access）和中间插入（Insertion）的权利，强行在动态数组（如 `std::vector`、`std::deque`）或链表（如 `std::list`）之上，套了一个**“后进先出（LIFO）”**的逻辑壳。
它的存在意义：**约束即力量**。通过极度受限的操作，换取了 O(1) 的极致性能，并在工程代码中提供了绝对清晰的语义表达（状态回溯、DFS 等）。

### 2. 动态数组实现（ArrayStack）的底层拷问
*   **物理形态：** 连续的物理内存。`top_index` 既记录了元素个数，也天然指向了**下一个可写入的空位**。
*   **缓存命中率（Cache Locality）降维打击：** CPU 按缓存行（Cache Line，通常 64 Bytes）读取内存。数组的连续性使得相邻元素被打包读入 L1 Cache。连续的高频 `push`/`pop` 几乎不产生 Cache Miss，速度碾压链表。
*   **扩容的均摊 O(1)：** 当容量满时，必须重新 `new T[2 * capacity]`，并迁移老数据。虽然单次扩容是 O(N)，但平摊到每次 `push` 上依然是 O(1)。在低延迟系统中，通常通过**预分配（Pre-allocation）彻底消灭扩容带来的毛刺。
*   **工程防守点：** 
    *   必须显式 `delete[] data` 防止内存泄漏。
    *   必须禁用拷贝构造和赋值运算符（`= delete`），严防浅拷贝导致的 Double Free（重复释放同一块内存）。
```cpp
ArrayStack(const ArrayStack &sta) = delete;
//注意一下这里一定要引用传递，否则就会调用拷贝构造，你又把拷贝构造禁用了
ArrayStack &operator=(const ArrayStack &) = delete;
```
### 3. 单向链表实现（LinkedStack）的底层拷问
*   **物理形态：** 散落在堆区（Heap）的非连续内存节点。
*   **为什么“栈顶即链表头”：** 如果栈顶在尾部，单向链表删除尾节点需要 O(N) 遍历找前驱。只有在头部进行插入（头插法）和删除，才能保证严格的 O(1)。
*   **伪头节点（Dummy Head）的陷阱：** ==栈**不需要** Dummy Head！==普通的链表用它来统一增删逻辑，但栈只在头部操作，Dummy Head 只会白白浪费内存，且容易导致 `top()` 误读垃圾值。
*   **隐形开销与内存碎片：** 每次 `push` 都调用 `new Node()`，涉及到与操作系统堆管理器的交互（甚至加锁、缺页中断），延迟不可控。频繁的 `push/pop` 会让堆区布满无法合并的**外部碎片（External Fragmentation）**。
*   **清道夫防线（析构函数）：** 必须手动遍历 `while (head != nullptr) { ... delete temp; }`，==绝不能漏删最后一个节点！==


### 4.优缺点辨析

1. **LinkedStack绝对的 O(1) 延迟保证（无扩容卡顿）**  
    你想想 ArrayStack。虽然它均摊复杂度是 O(1)，但当数组满了触发扩容时，它需要申请两倍的新内存，并把老数据全部 Copy 过去。如果是高频交易系统，或者硬实时（Hard Real-time）操作系统内核，这一瞬间的 O(n) 延迟可能会导致系统直接崩溃。  
    而 LinkedStack 没有任何动态扩容的负担。只要系统还能榨出哪怕一点点碎片的内存，它 的 push 永远是精确的几条汇编指令，延迟绝对稳定。
    
2. **对抗极端恶劣的物理内存环境**  
    ArrayStack 要求必须有一块**连续**的物理内存。如果你的物理内存总共还剩 1GB，但全被切成了几 KB 的碎片，你要申请一个 10MB 的 ArrayStack 是会直接失败（OOM）的。此时，LinkedStack 就能像水一样渗入这些碎片中，把它们利用起来。

### 什么是操作系统层面的 Call Stack（调用栈）？

#### 1. 内存空间的宏观物理模型
当你在操作系统中运行一个 C++ 程序时，OS 会给这个进程分配一块虚拟内存。你可以在脑海中画一个长方形：
* **最底部（低地址，比如 `0x00000000`）**：存放你的代码（Text 段）和全局变量（Data 段）。
* **中间部分**：就是 **Heap（堆）**。你用 `new` 申请的内存都在这里。堆是**从低地址向高地址生长**的。
* **最顶部（高地址，比如 `0x7FFFFFFF`）**：这就是我们的主角——**OS Stack（系统栈 / 调用栈）**。注意，物理上，**==栈是从高地址向低地址（向下）生长的！==**

#### 2. CPU 是怎么执行函数的？
假设你在玩一个单机游戏，正在打主线任务（`main` 函数），突然遇到了一个支线任务（调用了 `foo` 函数），你进入支线。支线打到一半，又触发了隐藏任务（调用了 `bar` 函数）。

CPU 只有一颗大脑，它必须知道：**我一会儿打完隐藏任务，怎么回到支线任务？打完支线，怎么回到主线？**

这就是 Call Stack 存在的唯一物理意义：**保存返回现场与局部变量**。

#### 3. 栈帧（Stack Frame）的物理构建过程
在 CPU 内部，有两个极其关键的指针寄存器：
* **`%rsp` (Stack Pointer, 栈顶指针)**：永远指向当前物理栈的最底部（因为栈向下生长，所以它指向有效数据的最低地址）。
* **`%rbp` (Base Pointer, 栈基址指针)**：像一个锚点，锚定当前正在执行的函数的栈底。

当 `main()` 调用 `foo(int a)` 时，微观物理层面发生了极其壮观的动作：

1. **压入参数**：把参数 `a` 压入栈。`%rsp` 向下移动（减小）。
2. **保存返回地址（Return Address）**：CPU 偷偷把 `main` 函数下一条指令的内存地址压入栈中。这相当于游戏存档点。
3. **保存老锚点**：把 `main` 的 `%rbp` 压入栈中保存（`push %rbp`）。
4. **建立新锚点**：把当前的 `%rsp` 赋值给 `%rbp`（`mov %rsp, %rbp`）。此时，`foo` 函数拥有了自己的“领地”。
5. **为局部变量分配空间**：`foo` 里面如果有 `int x, y;`，CPU 就直接把 `%rsp` 减去 8 个字节（向下移动 8 字节）。这 8 个字节的空间，就是 `x` 和 `y` 的物理家园！
```
[天花板: 高地址 1000]
-----------------------
|  main 的地盘        |
|  a = 1              |
----------------------- 
|  返回地址：做完回 main  |
-----------------------
|  foo 的地盘 (新栈帧)|
|  x = 10             |
|  y = 20             |
----------------------- <--- rsp向下移动了！(当前物理边界 980)
[地板: 低地址 0]
```
**【高能预警：物理虚无主义的终极体现】**
这一整块属于 `foo` 函数的内存区域（参数 + 返回地址 + 老 rbp + 局部变量），就叫一个 **“栈帧（Stack Frame）”**。

当 `foo()` 执行完毕（遇到 `return`）时，怎么销毁这块内存？
**根本不需要去清零内存！**
CPU 只需要：
1. 把 `%rsp` 直接提回 `%rbp` 的位置（废弃局部变量）。
2. 弹出老锚点，恢复 `main` 的 `%rbp`。
3. 弹出返回地址，告诉 CPU 下一步去哪执行。

```
[天花板: 高地址 1000]
-----------------------
|  main 的地盘        |
|  a = 1              |
----------------------- <--- rsp瞬间推回rbp！(回到 996)
|  返回地址：做完回 main  | (被遗弃)
-----------------------
|  (曾经的 foo 栈帧)  | 
|  x = 10             | (脏数据，依然留在物理内存里)
|  y = 20             | (脏数据，依然留在物理内存里)
----------------------- 
[地板: 低地址 0]
```
