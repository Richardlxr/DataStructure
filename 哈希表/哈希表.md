
# 开散列表
### 第一部分：灵魂拷问与物理模型

#### 1. 为什么我们需要哈希表？（工程视角的“魔法”）
在你学过的知识里：
*   **数组（顺序表）**：为什么能做到 $O(1)$ 查找？因为它的底层是连续内存。只要你给我一个**整数索引** `i`，底层 CPU 马上就能通过 `Base_Address + i * sizeof(Element)` 算出物理地址。**本质上，数组是用“空间连续性”换取了“时间极速”。**
*   **链表**：为什么查询是 $O(N)$？因为内存在物理上是散乱分布的，只能靠指针一根一根顺藤摸瓜。

**灵魂拷问来了：** 如果我的查询条件不是整数索引 `i`，而是一个字符串 `"Apple"` 或者是某个用户的 ID `USER_89757`，你怎么在 $O(1)$ 的时间内找到它在内存里的位置？数组直接罢工了，因为 `"Apple"` 不能参与内存地址的数学计算。

**哈希表的魔法就在于：** 它充当了一个“翻译官”。它通过一个**哈希函数（Hash Function）**，把任何稀奇古怪的 Key（比如 `"Apple"`），通过复杂的位运算和数学搅和，强行变成一个**整数**。
然后，拿着这个整数去对底层数组的长度**取模（Mod）**，得到一个合法的数组索引 `i`。
这样，我们就能继续享受数组 `Base_Address + i * sizeof(Element)` 带来的 $O(1)$ 寻址快感！

#### 2. 哈希表的底层物理结构到底是什么？

在你的草稿纸上画一个数组，但请注意，**这个数组里存的不是具体的数据，而全是指针！**（在 C++ 里，它是一个 `Node**` 或者 `vector<Node*>`）。我们管这个数组叫 **“桶（Buckets）”**。

这就会引出哈希表最致命的问题——**哈希冲突（Hash Collision）**。
宇宙中的字符串是无限的，但你的底层数组长度是有限的（假设长度是 8）。根据抽屉原理，哪怕你的哈希函数再精妙，必然会出现两个不同的 Key，算出来的数组索引是一样的（比如 `"Apple"` 和 `"Banana"` 算出来的索引都是 3）。

**怎么防守？怎么解决冲突？**
这就是你刚学过的**单向链表**大显身手的时候了！工程上最经典的解法叫**拉链法（Separate Chaining）**。
既然 `"Apple"` 和 `"Banana"` 都抢着要进 3 号桶，那 3 号桶里干脆不存具体数据，而是存一个**单向链表的头指针（Head Pointer）**！
*   先来的 `"Apple"` 作为一个链表节点，挂在 3 号桶上。
*   后来的 `"Banana"` 发现 3 号桶已经有 `"Apple"` 了，没关系，再 `new` 一个节点，用你烂熟于心的链表防守型连线手法，把 `"Banana"` 串在 `"Apple"` 后面（或者插在最前面）。

所以，哈希表的底层物理真相就是：**动态数组 + 多个单向链表**的缝合怪！


#### 哈希冲突的解决方案

“如果一个桶里有很多东西（链表很长），那我遍历这个链表的时候，时间复杂度不就是 $O(N)$ 了吗？凭什么说哈希表查找是 $O(1)$ ？”

**答案是：**
你说的完全正确！**在极端最坏的情况下（比如哈希冲突极其严重，所有元素都挤在同一个桶里），哈希表的查找时间复杂度确实会退化成 $O(N)$！** 这时候它跟一个普通链表没有任何区别，完全是个废柴。

##### 1. 为什么平时敢说是 $O(1)$？
在理想情况下（或者说工程平均情况下），我们的哈希函数设计得足够好（比如把数据像撒胡椒面一样均匀地撒在每个桶里），并且**桶的数量足够多**。

假设你有 1000 个数据，但我给你准备了 1000 个桶（甚至更多）。
*   理想情况下，每个桶里大概率只有 1 个节点，或者 0 个。
*   偶尔有一两个桶里有 2 个节点。
*   你要查找任何一个数据，计算一次哈希值（$O(1)$），定位到桶（$O(1)$），然后遍历一个长度仅为 1 或 2 的链表（$O(1)$）。
**总耗时：$O(1)$。**

##### 2. 怎么防止退化成 $O(N)$？（扩容机制）

这才是哈希表工业级实现的核心秘密！
**哈希表绝对不会允许链表无限变长！**

它内部有一个监控指标叫**负载因子（Load Factor）**：
$$ \text{Load Factor} = \frac{\text{元素总个数 } N}{\text{桶的总数 } M} $$

在 Java 的 `HashMap` 或 C++ 的 `unordered_map` 里，这个阈值通常默认是 **0.75**。
意思是：**只要元素总个数超过了“桶数 × 0.75”**（比如你有 100 个桶，存了 76 个元素），哈希表就会**立刻触发扩容（Rehash）！**

**扩容发生了什么？**
1.  **申请新数组**：开辟一个两倍大的新数组（比如 200 个桶）。
2.  **大搬家**：遍历旧数组里的所有链表节点。
3.  **重新计算**：拿着每个节点的 Key，用新数组的长度（200）重新取模：`hash(key) % 200`。
4.  **分散落位**：原本挤在同一个桶里的兄弟，现在因为取模数变了（比如 `5 % 8 = 5`，但在 `5 % 16 = 5`；而 `13 % 8 = 5`，但在 `13 % 16 = 13`），它们会被拆散，均匀地分布到新数组的不同桶里去了！

### 第三部分：C++ STL 实战指南

在现代 C++ 中，哈希表的标准实现叫 **`std::unordered_map`**。
名字里的 `unordered`（无序）恰恰暴露了它的物理本质——由于数据是被哈希函数“随机”散列到各个桶里的，所以你遍历它的时候，**输出顺序跟你插入的顺序毫无关系**。

#### 1. 增、删、改、查、遍历的工程标准
假设我们用哈希表存学号（int）和姓名（string）：
```cpp
#include <unordered_map>
#include <string>

std::unordered_map<int, std::string> map;

//可以预分配内存
std::unordered_map<int,int > map;
map.reserve(100);
```

*   **插入与修改（增/改）**
    1. 最常用的就是 `[]` 操作符：
	    `map[101] = "Alice";`
	    这句代码在底层干了什么？如果 101 不存在，它会立刻哈希算桶号、`new` 一个节点挂上去；如果 101 已经存在，它会遍历那个桶的链表找到 101，把 Value 覆盖成 "Alice"。
	2. 或者用带返回值的insert函数防止覆盖：
		```cpp
		// 尝试插入 101 -> Alice
		auto result = map.insert({101, "Alice"});
		
		//注意这里要用{}把键和值包裹起来

		// result.second 是一个 bool 值，告诉你插入成功没有
		if (result.second == false) {
	    // 插入失败！说明 101 已经存在了！
	    // 可以在这里报错，或者生成一个新的 Key 再试
		}
		```

*   **致命的查询（查）—— 防守型编程的重灾区！**
    **绝对、绝对、绝对不要用 `if (map[101] == "Alice")` 来判断键是否存在！**
    在 C++ 里，`[]` 操作符极其“手贱”。如果你查询一个不存在的 Key（比如 `map[999]`），它不会报错，而是会**自作主张地在底层给你 `new` 一个节点，Key 是 999，Value 是空字符串**！这会导致哈希表里塞满垃圾无效节点，甚至引发频繁的底层扩容，内存直接爆炸。
    **标准防守写法：必须用 `find()` 迭代器！**
    ```cpp
    auto it = map.find(101); // O(1) 寻找的是键！！！！
    if (it != map.end()) {
        // 找到了！通过迭代器安全获取
        // it->first(键) 是 101，it->second(值) 是 "Alice"
    } else {
        // 没找到，安全退出，什么多余的内存都不会分配
    }
    ```

*   **删除（删）**
    `map.erase(101);` （底层其实就是在做你熟悉的单向链表节点删除，修改前驱节点的 `next` 指针，然后 `delete` 释放内存）。
	- 其中的逻辑
	1. **哈希计算**：哈希表拿到你要删除的 Key（也就是 101）。它立刻把 101 扔进哈希函数，算出哈希值，然后对底层的数组长度（假设当前数组长度是 8）取模。假设 `101 % 8 = 5`。
	2. **定位桶**：哈希表找到了底层数组的**第 5 号桶**（`buckets[5]`）。
	3. **遍历单向链表**：5 号桶里可能挂着一条单向链表，里面存着学号为 101、109、117 的三个学生（因为它们对 8 取模都是 5，发生了冲突）。
	4. **精确打击与删除**：哈希表顺着 5 号桶的链表往下找：“你是 101 吗？不是，你是 109。”继续往下找：“你是 101 吗？是的！”
	
注：哈希表的节点里面有键也有值，类似
   ```cpp
   struct HashNode {
    int key;       // 必须存 Key！这就是为了解决冲突后能认出谁是谁！
    string value;  // 存 Value
    HashNode* next; // 指向下一个冲突的兄弟
};
   ```
   
3. **物理断线**：找到 101 所在的那个节点后，执行你最熟悉的单向链表节点删除操作（把 101 前一个节点的 `next` 指针，连到 101 的下一个节点上），然后 `delete` 掉 101 这个节点所在的内存。

*   **遍历（遍历桶和链表）**
    切记加上 `const auto&` 引用，防止深拷贝字符串浪费内存！
    ```cpp
    for (const auto& kv : map) {
        // kv.first 是 key，kv.second 是 value
    }
    ```

# 闭散列表（Closed Hash Table）

## 🌟 一、 核心物理模型
**定义**：闭散列表（又称开放定址法），是一种**绝对不使用链表指针**的哈希冲突解决方案。
**物理本质**：从头到尾只有一个纯粹的**动态数组**。
**直观比喻**：**“抢车位”模型**。如果算出来的专属车位被占了，就摇下车窗，按照某种规则在停车场里继续找下一个空车位。

## ⚔️ 二、 冲突探测规则（找车位策略）
当 `hash(key)` 算出的初始位置 `initPos` 发生冲突时，通过加上偏移量 $d_i$ 寻找下一个位置：$pos = (initPos + d_i) \% size$。

1. **线性探测法 (Linear Probing)**
   * **规则**：$d_i = 1, 2, 3, ...$（挨个往后找）。
   * **致命缺点**：**初级聚集（Primary Clustering）**。冲突的数据会像滚雪球一样连成一片，导致后面来的数据要跨过长长的“拥堵路段”才能找到空位，性能退化严重。
2. **二次探测法 (Quadratic Probing)**
   * **规则**：$d_i = 1^2, -1^2, 2^2, -2^2...$（跳着找）。
   * **优点**：打破了连成一片的初级聚集。
   * **缺点**：同义词（哈希值相同的数据）依然会有相同的探测轨迹，称为**二次聚集**。
3. **双重散列法 (Double Hashing)**
   * **规则**：遇到冲突时，用**第二个哈希函数**算出一个步长，每次按照这个自定义步长跳跃。
   * **优点**：最不容易发生聚集，分布最均匀。

## 🪦 三、 灵魂机制：状态机与“墓碑（Tombstone）”
**痛点**：在闭散列中，如果直接将节点删除（清空数据），会发生**“断链灾难”**。因为后续因冲突而顺延存储的元素，在查找时遇到这个被清空的空位，会误以为后面没数据了，从而导致查找失败。

**工业级解法**：为每个节点引入 `state` 字段，维护一个 3 态机制：
* 🟢 **`0` (Empty)**：纯天然空位。表示这里从未存过数据。**查找的终止信号**（遇到 0 说明后面绝对没戏了）。
* 🔵 **`1` (Active)**：正常使用中。存有有效数据。
* 🔴 **`2` (Deleted)**：**墓碑！** 数据已被删除。这是一个**通行信号**（告诉查找程序：“这辆车开走了，可以停新车，但我身后的车位可能还有顺延过来的车，请跨过我继续找！”）。

```cpp
// 闭散列节点标准定义
struct HashNode {
    int key;
    int value;
    int state; // 0-Empty, 1-Active, 2-Deleted
};
```

## ⚙️ 四、 核心操作流 (基于线性探测)

### 1. 查找 (Find)
* 算出初始位置，进入 `while` 循环。
* 遇到 `state == 0` $\rightarrow$ 彻底断线，返回 `NotFound`。
* 遇到 `state == 1` 且 `key` 匹配 $\rightarrow$ 找到了，返回 `Value`。
* 遇到 `state == 2`（墓碑）或 `state == 1` 但 `key` 不匹配 $\rightarrow$ **无视它，继续往下找** `pos = (pos + 1) % size`。

### 2. 删除 (Remove)
* 逻辑同 Find。
* 找到目标节点后，**绝对不清除数据，只把 `state` 改为 `2`**（立碑）。

### 3. 插入/更新 (Insert)
* **标准逻辑**：遇到 `state == 0` 或 `state == 2`，直接覆盖写入，并将 `state` 改为 `1`。

## 🚨 五、 进阶与面试高频陷阱

### 陷阱 1：死循环危机
如果哈希表装满了，或者全都是墓碑，线性探测会绕回起点（`pos == initPos`）。**必须在循环条件中加入防死循环机制**：`while (pos != initPos)`，一旦绕回原点说明表已满，需触发扩容。

### 陷阱 2：墓碑导致的“重复 Key”灾难（大厂必考）
* **场景**：假设 5 号位是 `key=15` 的墓碑，6 号位是实际存活的 `key=15`（当年冲突顺延过去的）。现在用户要求更新 `key=15` 的值为新数据。
* **新手做法**：查到 5 号位是墓碑，狂喜，直接把新数据存在 5 号位。
* **灾难结果**：哈希表里同时出现了两个 `key=15`（5号和6号）。以后查找永远只能找到 5 号。
* **工业级正解（延迟插入策略）**：
  在 Insert 遍历时，如果遇到墓碑，**不要立刻插入！** 用一个临时变量记下第一个遇到的墓碑位置（比如记下 5 号），然后**继续往后找**。
  1. 如果后面找到了活跃的 `key=15`，直接在后面的位置**更新**。
  2. 如果一直往后找，遇到了 `state == 0`（确定后面绝对没有 15 了），这时候才掉头，把新数据插入到刚才记下的 5 号墓碑处。

## 🆚 六、 闭散列 (开放定址) vs 开散列 (拉链法)
| 特性                    | 闭散列 (Closed Hashing / 纯数组)   | 开散列 (Open Hashing / 数组+链表) |
| :-------------------- | :--------------------------- | :------------------------- |
| **内存分配**              | 一次性分配大数组。无链表，**无内存碎片**。      | 冲突时频繁 `new` 节点，容易产生内存碎片。   |
| **缓存命中率 (CPU Cache)** | **极高**（连续内存，CPU 预读极其友好）。     | 较低（指针乱飞，内存不连续）。            |
| **空间利用率**             | 需保持较低的负载因子（一般 < 0.5），否则聚集严重。 | 负载因子可以较高（一般 0.75 甚至 1.0）。  |
| **删除操作**              | 极其复杂，必须引入“墓碑机制”。             | 极其简单，正常的单链表节点删除即可。         |
|                       |                              |                            |
